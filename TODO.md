Ordered by effort/risk, not by page importance — cheapest, lowest-risk wins first. Detail for each item lives in its matching `##` section below (backend items under `# Backend TODO's`, frontend items under `# Frontend TODO`), each tagged `— Phase N`.

- **Phase 1 — DONE.** Turned out to need a bit more than "pure reuse, no new backend work" as first estimated: Carbon Intelligence's per-region drill-down needed one small backend addition (optional `region` param on `GET /v1/emissions/timeseries`), and Forecast Explorer's Horizon selector had to be removed rather than wired, since `GET /v1/forecast` ignores requested horizon/interval entirely. Settings' Users/Organizations tabs *were* a clean frontend-only swap as predicted — calling IAM's real `/v1/users`/`/v1/orgs` directly using the session the dashboard already holds from login, **no auth-bridging needed**, though both real models turned out narrower than the mock assumed (no RBAC role, no org industry/plan/emissions fields). See each page's own `##` section below for details.
- **Phase 2 — new endpoints, reusing the now-proven "public projection" pattern (4th time).** Data Sources and Data Quality & Anomalies need one or two new unauthenticated `/public/*` routes on `data-pipeline`, same recipe as `/v1/data-quality/summary/public` and the 4 Ingestion endpoints. Operations' and Operational Tasks' pipeline-shaped widgets need **zero new backend** — they just reuse Ingestion's already-built public pipelines/runs endpoints.
- **Phase 3 — genuinely new, moderate backend effort (cross-service, not single-service).** System Health and Operations' service-health cards need a real multi-service health view. No single endpoint provides this; recommend client-side multi-fetch across each of the 3 services' own (differently-shaped) health endpoints over building a 4th aggregator service.
- **Phase 4 — blocked on product decisions, not engineering.** Energy Analytics (corporate Scope 1/2/3 accounting — no backend domain, arguably out of scope for a grid-intelligence platform), Reports (regulatory report generation — no engine exists), Model Registry + Training & Experiments + the ML-ops halves of Operations/Operational Tasks (real history only exists in MLflow itself, a 4th, unproxied backend — needs a decision: proxy it, link out to it, or stay mock).

## MLflow / training history — needs a decision before any engineering — Phase 4

Real historical training runs/experiments only exist in MLflow itself (the `mlflow` container in `docker-compose.yml`), which has its own REST tracking API, its own port, and an auth/CORS situation never verified for direct browser use. Neither forecast-api nor data-pipeline proxies it — forecast-api's `GET /v1/model` is a real but thin *current-snapshot* (status/version/stage/metrics of what's loaded now), not run history. `data-pipeline`'s `dbt` router (`POST /v1/dbt/{build,run,test}`) is trigger-only too — no GET/status/history endpoint exists there either, so it can't back a "past runs" view even for warehouse builds.

Three real options, needs a call:

1. Build a thin proxy (forecast-api or data-pipeline) over MLflow's tracking API — keeps auth/CORS consistent with the rest of the platform, but is genuinely new backend work, not a wiring task.
2. Link Model Registry and Training & Experiments out to the real MLflow UI instead of pretending to embed live data client-side.
3. Leave both pages honestly mock, labeled illustrative (same treatment already given to the Ingestion page's "Builder" tab).

Not deciding here — this blocks Phase 4's Model Registry/Training/ML-ops items until picked.
