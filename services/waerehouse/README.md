# Warehouse Micro-Service

Here is an implementation task list focused specifically on the Event-Driven Warehousing Service and its direct integrations with DuckDB, RabbitMQ, PostgreSQL (NeonDB), and dbt.

**Status (2026-08-06): all 5 phases implemented and live-verified against real infrastructure** (real NeonDB, real RabbitMQ, real Cloudflare R2 — not mocked/simulated). 55 tests passing, `ruff check`/`ruff format --check`/`mypy app` all clean. See each item below for what was actually built and how it was verified.

Standalone extraction of `data-pipeline`'s warehousing half — own `uv` project (`services/waerehouse`, package `app`), same extraction pattern `services/ingestion` already established for the fetch/stage half. Runs *alongside* `data-pipeline`'s own `warehouse_sync` consumer (unmodified, still live — see `Settings.warehouse_sync_consumer_enabled`, `TODO.md` Phase 4) until this service is verified and explicitly cut over — not a replacement yet, same "extract, don't replace yet" decision `services/ingestion` made.

## Storage Policy

`raw.*`'s rolling 60-day retention (Phase 3 below, `Settings.retention_days`) applies **only** to `raw.*`. It does **not** apply to `raw_marts.*` — the 4 time-series `fct_*` marts are `materialized: incremental` specifically so a `dbt run` never rebuilds them from `raw.*`'s current (pruned) contents (`TODO.md` Phase 1; the marts used to be `table`-materialized, which *did* silently inherit `raw.*`'s 60-day floor on every run — fixed, not a hypothetical). `raw_marts.*` keeps accumulating indefinitely; nothing in this service prunes it. Stated explicitly here so a future "let's simplify the marts back to `table`" change doesn't unknowingly reintroduce the Phase 1 bug.

## Phase 1: Core Service Setup & Infrastructure Foundation

[x] **Project Structure & Environment**: `services/waerehouse/` — `app/{core,db,consumers,loaders,retention,dbt,api,schemas}/`, `pyproject.toml` (own `uv` project, package `app`, `dbt-postgres`/`aio-pika`/`aioboto3`/`pyarrow`/`fastapi`/`sqlalchemy` deps), `.env`-based config (`pydantic-settings`, `app/core/config.py`). `app/core/{logging,errors,middleware}.py` ported verbatim from `services/ingestion`'s identical fully-generic modules.

[x] **Database Connection Pools**: `app/db/session.py` — async SQLAlchemy engine/session for NeonDB (`statement_cache_size=0` for the Neon pooler, same fix `services/ingestion`/`data-pipeline` already needed). `app/db/duckdb_client.py` — read-only access to the *same* shared `landed.duckdb` file `services/ingestion` writes into (`Settings.duckdb_staging_dir`, same default so the Docker shared-volume trick that already works for ingestion↔data-pipeline works here too — see Phase 2's own note on this). This service never opens the DuckDB file read-write; DuckDB allows unlimited concurrent readers, just one writer, and writing stays ingestion's job. Tests: `tests/test_duckdb_client.py`.

[x] **RabbitMQ Consumer Framework**: `app/db/rabbitmq.py` — `aio_pika.connect_robust` (automatic reconnection), manual ack/nack, `prefetch_count=1`. **Real finding while building this**: `ecolens.landing` already exists live, declared *without* a DLX by `services/ingestion`'s publisher — redeclaring it here with `x-dead-letter-exchange` would raise `PRECONDITION_FAILED` (confirmed directly against the real broker's management API before writing any code, not assumed). Dead-lettering is instead handled at the **application level**: a separate, freshly-declared `ecolens.landing.dlx`/`.dlq` that a failed message's body + error gets explicitly published to, then the original message is acked off the main queue (never nacked-and-requeued, which would loop forever). Tests: `tests/test_rabbitmq.py` (7 tests — success path, DLX topology declaration, failure → DLQ + ack, unparseable JSON, metric increments, connection lifecycle).

## Phase 2: Staging & Bounded Raw Ingestion Pipeline (`raw.*` Schema)

[x] **PostgreSQL Schema Provisioning**: `app/migrations/0001_raw_schema.sql` (idempotent, formally establishes this service's own ownership of `raw.*`) + `scripts/apply-migrations.sh`. **Real bug found and fixed live**: the *original* `raw.*` schema (copied from `data-pipeline`'s own migrations) didn't match what `services/ingestion` actually stages today at all — missing per-fueltech columns (`coal_mw`/`gas_mw`/...), `price` vs. the real `price_mwh`, `openelectricity_mix` defined long-form when it's actually landed wide-form, `aemo_holidays`'s `date`/`is_workday` never modeled. Confirmed via `DESCRIBE` against the real shared DuckDB file, then confirmed **every single `raw.*` table was completely empty** (0 rows, all 5) — meaning this mismatch had silently broken the DuckDB→Postgres sync path for every source from the start, not just for this new service. `app/migrations/0002_fix_raw_schema_to_match_real_ingestion_output.sql` drops and recreates the 5 tables with the real column shapes (safe — zero data to lose). Applied live against the real NeonDB. Turned out `data-pipeline`'s own dbt staging models already expected exactly this corrected shape (see Phase 4) — only the raw DDL itself was stale.

[x] **DuckDB-to-PostgreSQL Transfer Logic**: `app/consumers/landed_events.py` (`sync_landed_event`, this service's own version of `data-pipeline`'s `warehouse_sync.sync_landed_event`, adapted for `services/ingestion`'s newer shared-DuckDB-file layout) + `app/loaders/postgres_loader.py` (`load_to_postgres`, ported from `data-pipeline`'s identical function — COPY into a temp table, then `INSERT ... ON CONFLICT DO NOTHING`). Closes `meta._ingest_log` out to `success`/`sync_failed` (`app/loaders/ingest_log.py`, ported from `data-pipeline`'s `log_run_synced`/`log_run_sync_failed`) — same audit-trail contract `services/ingestion` starts. Tests: `tests/test_postgres_loader.py`, `tests/test_landed_events.py`.

[x] **Idempotent Load Handling**: the natural key *is* the dedup key — every `raw.*` table's `PRIMARY KEY` (`ts`/`date` + region/station/fuel-type) drives `ON CONFLICT DO NOTHING`, no separate payload-hash column needed. **Live-verified end-to-end** (not just unit tests): staged a synthetic row into the real shared DuckDB file, ran the real consumer handler against it, confirmed it landed in real Postgres; ran the exact same sync a second time and confirmed `rows_loaded: 0` (genuinely 0 new inserts, not an error) while the row count stayed at 1 — true idempotency, not just "didn't crash".

## Phase 3: Rolling-Window Retention & Storage Enforcement (Critical for Free Tier)

[x] **Automated Data Pruning Job**: `app/retention/pruning.py` (`prune_raw_tables`, default 60-day window, `Settings.retention_days`) — deletes from the 4 real time-series `raw.*` tables (`aemo_holidays` deliberately excluded, same reasoning `services/ingestion`'s own ML training/backfill already applies: annual snapshot, not a rolling time series). **Manually/cron-triggered** (`ecolens-warehouse prune`), not a background scheduler baked into the service — same conservative default `services/ingestion`'s own `retention.py`/`ml_anomaly.py` established this session; README's own "pg_cron or Celery Task" framing already implies an external scheduler calls in, not the service scheduling itself. Tests: `tests/test_pruning.py`.

[x] **Vacuum & Bloat Management**: `app/retention/vacuum.py` (`vacuum_analyze_raw_tables`) — `VACUUM ANALYZE` on the same 4 tables, via a raw `AUTOCOMMIT`-isolation connection (`VACUUM` can't run inside a transaction block, which a plain session always opens). **Live-verified** against the real NeonDB (`ecolens-warehouse vacuum`) — succeeded on all 4 tables.

[x] **Database Size Monitoring & Alerting**: `app/retention/size_monitor.py` (`check_database_size`) — the real `pg_database_size(current_database())` figure (the same number Neon's own dashboard shows), classified against `Settings.database_size_limit_mb` (500MB) at `retention_warning_pct`/`retention_emergency_pct` (80%/95%) thresholds, pushed to the `ecolens_warehouse_database_size_bytes` Prometheus gauge. **Live-verified**: real DB currently at 4.3% (`severity: ok`). Exposed via `GET /v1/pipeline/storage` and `ecolens-warehouse check-size` (nonzero exit at warning-or-worse, for cron/CI use). Tests: `tests/test_size_monitor.py`.

[x] **Cloudflare R2 Cold-Storage Export**: `app/retention/cold_storage.py` (`export_and_prune`) — exports a table's about-to-expire rows to a Parquet file in R2 (`app/db/object_storage.py`, this service's own copy of `services/ingestion`'s identical S3-compatible client, same account/bucket) *before* deleting them, never the other way around; a table whose export fails is simply skipped that run (isolated per-table, same "one bad unit shouldn't halt everything" philosophy the RabbitMQ consumer/`services/ingestion`'s Celery fan-out already use), not left half-pruned. Idempotency-checked (`object_exists`) the same way `services/ingestion`'s staged-run uploads already are. `ecolens-warehouse export-and-prune` is the recommended entrypoint over plain `prune`. Tests: `tests/test_cold_storage.py`.

## Phase 4: Transformation Engine Integration (dbt)

[x] **dbt Project Initialization**: the *entire* existing `data-pipeline/dbt/ecolens` project (15 models across staging/intermediate/marts, 51 data tests, source declarations, 1 seed) ported verbatim into `services/waerehouse/dbt/ecolens` — this project was already real and mature, just needed to actually run from its new home. `app/dbt/runner.py` (ported from `data-pipeline`'s `dbt_runner.py`) shells out to the real `dbt` CLI; `Settings.dbt_postgres_env`/`dbt_project_dir` (ported from `data-pipeline`'s identical properties, `dbt_project_dir` fixed to resolve against this package's own root rather than a bare relative string — the exact class of bug `services/ingestion`'s `duckdb_staging_dir` hit earlier this session) derive dbt's `profiles.yml` env vars from this service's own single `DATABASE_URL`. `ecolens-warehouse dbt <subcommand>` CLI entrypoint.

[x] **Source Declarations (`sources.yml`)**: already real in the ported project (`models/staging/_sources.yml`) — per-source freshness tests (`warn_after`/`error_after`), `loaded_at_field: ingested_at`. No changes needed.

[x] **Incremental dbt Models**: staging = view, intermediate = ephemeral (`dbt_project.yml`'s own materialization config, unchanged from the ported project). **Correction (2026-08-06, `TODO.md` Phase 1)**: marts were originally *all* `table` — a full `CREATE TABLE AS SELECT` rebuild off `raw.*` on every `dbt run`. Combined with `raw.*`'s own 60-day retention (Phase 3), this silently dropped mart history older than 60 days on every run, contradicting this README's own Storage Policy ("curated tables retain the complete historical dataset"). The 4 time-series `fct_*` marts are now `+materialized: incremental` (`delete+insert`, per-model `unique_key`) so a `dbt run` only adds/replaces the recent slice instead of rebuilding from whatever's currently left in `raw.*`; the 2 `dim_*` marts (small reference sets, not time series) stay `table`. **Live-verified against a real Postgres 16 container**: seeded 10 days of synthetic `raw.*` data, ran `dbt run` (full first build, 2869 rows in `fct_energy_demand`), then pruned `raw.*` down to the last 3 days (simulating the retention job) and added a few new rows (simulating the next ingestion cycle), then ran `dbt run` again — the mart kept its full 10-day history (`min(ts)` unchanged), picked up the new rows, and introduced zero duplicate keys. `dbt test` still passes (the one pre-existing failure, `assert_national_intensity_within_tolerance`, is a documented placeholder-value test unrelated to this change — fails against any synthetic fuel mix that doesn't match the real NEM average).

[x] **Data Quality Testing**: 51 `not_null`/`unique`/`relationships` tests, already real in the ported project. **Live-verified, fully, against the real corrected schema**: `ecolens-warehouse dbt debug` (all checks pass, real NeonDB connection confirmed) → `dbt seed` (14-row `emissions_factors` seed loaded) → `dbt run` (all 11 models — 5 staging views + 6 marts tables — built successfully) → `dbt test` (**all 51 tests PASS**). This is what actually proved the Phase 2 schema fix was correct, not just structurally plausible.
